# Static Analysis (Correctness & Maintainability)

## 1. Code quality issues: dead code, duplication, excessive complexity
- `packages/pi-agent-core/src/proxy.ts:86` — **warning** — `streamProxy` is documented as the way to proxy LLM calls, but it is not exported (and appears unused). This makes the example code in the doc comment non-functional and risks the implementation drifting as “dead” code. **Fix:** export `streamProxy` (and keep the public surface intentional), or remove the doc/example and keep it as an internal helper with a clear non-public name.
- `src/update-check.ts:22` and `src/resources/extensions/gsd/changelog.ts:23` — **suggestion** — Duplicate `compareSemver` implementations increase divergence risk (behavior changes in one place but not the other). **Fix:** share a single helper (or adopt a dedicated semver parser) and reuse it in both call sites.
- `packages/pi-agent-core/src/agent-loop.ts:175` — **suggestion** — `runLoop` couples multiple concerns (LLM streaming, tool execution, steering/follow-up queues, termination, and error reporting) in nested loops, making edge cases harder to reason about. **Fix:** extract “turn execution”, “tool execution”, and “queue/termination” into smaller helpers and add focused tests for cross-product edge cases (pauseTurn + steering + follow-up).

## 2. Naming and readability concerns
- `packages/pi-agent-core/src/proxy.ts:277` — **suggestion** — The implementation relies on an ad-hoc hidden field (`partialJson`) stored via `as any`, which obscures the true shape of in-flight tool call objects and makes the code harder to maintain. **Fix:** model an explicit internal type (e.g., `type PartialToolCall = ToolCall & { partialJson: string }`) and store it without `any`, or keep a side-table keyed by `toolCallId`.
- `src/headless-query.ts:76` — **suggestion** — `loadExtensionModules()` returns a bundle of loosely-typed functions sourced from dynamic module imports; the implicit contract is not obvious at the call site. **Fix:** define an explicit `ExtensionModules` interface and return that type (plus a small runtime validator) so failures are self-describing.

## 3. Error handling gaps: uncaught exceptions, missing validation
- `packages/pi-agent-core/src/proxy.ts:166` — **critical** — `JSON.parse(data)` is performed on every SSE `data:` line without per-line guarding; any non-JSON payload (keepalive frames, `[DONE]`, truncated JSON, or server bug) throws and terminates the entire stream. **Fix:** wrap the per-line parse in its own `try/catch` and either ignore malformed frames (with optional debug logging) or convert them into a structured proxy error event.
- `packages/pi-agent-core/src/proxy.ts:180` — **critical** — On “normal” stream completion, the code calls `stream.end()` without pushing a terminal `{type:"done"}`/`{type:"error"}` event and without passing a result to `end(result)`. `EventStream.result()` will never resolve in this case, which can hang consumers that await the final message (e.g., agent loop code that calls `response.result()`). **Fix:** ensure one of the following always happens: (a) push a final `done` event, or (b) call `stream.end(partial)` with a final `AssistantMessage` result when the underlying HTTP stream ends without an explicit proxy `done/error`.
- `packages/pi-agent-core/src/agent-loop.ts:769` — **warning** — `afterToolCall` hook errors are not contained. If `afterToolCall` throws, it bubbles up and terminates the entire agent loop via the outer `try/catch`, converting what is effectively a “post-processing hook bug” into a full session failure. **Fix:** wrap `afterToolCall` in `try/catch`; on failure, emit a tool result error (or keep original result) and optionally report the hook error via telemetry.
- `src/headless-query.ts:76` — **warning** — Dynamic module loading uses `as any` and assumes exported members exist (e.g., `deriveState`, `resolveDispatch`). Missing/renamed exports or load failures will throw with low-context errors. **Fix:** validate module shapes at runtime (e.g., check `typeof stateModule.deriveState === "function"`) and throw a single aggregated error that includes which module/exports were missing and the resolved paths.
- `src/update-check.ts:134` — **warning** — Cache contents are not validated before use. If `.update-check` parses as JSON but has wrong types (e.g., `latestVersion` not a string), `compareSemver(cache.latestVersion, …)` can throw, rejecting the update check. **Fix:** validate `lastCheck` is a number and `latestVersion` is a non-empty string; otherwise treat cache as missing and rewrite it on next successful fetch.

## 4. Type safety issues (if applicable)
- `src/headless-query.ts:77` — **warning** — Extensive `as any` casts on dynamically imported extension modules weaken type guarantees and can hide API drift until runtime. **Fix:** define an `ExtensionModules` interface + runtime guards, and reduce `any` to a narrow `unknown` validated at boundaries.
- `packages/pi-agent-core/src/agent.ts:557` — **suggestion** — `(event.message as any).errorMessage` and `catch (err: any)` reduce safety and complicate refactoring. **Fix:** use `unknown` in catch blocks and implement a type guard like `isAssistantWithErrorMessage(message): message is AssistantMessage & { errorMessage: string }`.
- `packages/pi-agent-core/src/proxy.ts:290` — **suggestion** — `(content as any).partialJson` relies on unchecked mutation of a value typed as `ToolCall`, increasing the chance of runtime shape mismatches. **Fix:** use a typed wrapper or a side-map for partial JSON accumulation.

## 5. Dependency concerns: outdated, unused, or risky packages
- `package.json:133` — **suggestion** — `hosted-git-info` is declared in the root dependencies but its only in-repo import is in `packages/pi-coding-agent/src/utils/git.ts:1` (the package also declares it). This can be harmless under hoisting, but it increases ambiguity about which `package.json` “owns” the dependency. **Fix:** remove root-level declarations that are not used by root code, and keep dependencies declared where they are actually imported (or standardize on workspace-level dependency policy explicitly).
- `package.json:143` and `packages/pi-coding-agent/package.json:43` — **suggestion** — Duplicated workspace dependencies (example: `sql.js`) increase version-skew risk if constraints diverge. **Fix:** align versions and document whether the monorepo expects duplication (for publishable packages) vs hoisting-only (for root tooling).
- `package.json:127` and `packages/pi-coding-agent/package.json:31` — **suggestion** — `chalk` version constraints differ between root and `@gsd/pi-coding-agent`, which can lead to multiple installed versions and subtle behavioral differences in formatting. **Fix:** align semver ranges across workspaces where feasible.

## 6. Test coverage observations
- `src/tests/update-check.test.ts:52` — **suggestion** — Update-check tests cover malformed JSON but do not cover “valid JSON with wrong types” (e.g., `{ "lastCheck": "x", "latestVersion": {} }`) which can currently flow into `compareSemver` via `checkForUpdates()` (`src/update-check.ts:134`). **Fix:** add a regression test for wrong-type cache content and update `readUpdateCache` (or callers) to validate schema before use.
- `packages/pi-agent-core/src/proxy.ts:86` — **warning** — No dedicated unit tests are visible for proxy streaming behavior (per-line parse robustness, abort behavior, and ensuring `.result()` resolves on end). Given the failure mode can be a hang (`packages/pi-agent-core/src/proxy.ts:180`), this is high-value to lock down. **Fix:** add tests that feed synthetic SSE frames (including malformed frames and missing terminal events) and assert the stream terminates with a resolved result.
- `src/headless-query.ts:76` — **suggestion** — There is an e2e smoke test for the command path (`src/tests/integration/e2e-smoke.test.ts:507`), but not for failure modes like missing extension exports or load failures. **Fix:** add a unit test for `loadExtensionModules()` that stubs the loader/import path resolution and asserts the runtime validator produces actionable errors.

### Positive notes

- `packages/rpc-client/src/jsonl.ts:21` — The JSONL framing logic explicitly avoids `readline` pitfalls and documents the rationale well, which reduces future “helpful refactor” regressions.
